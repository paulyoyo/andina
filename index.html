— Capítulo 1 / Diagnóstico

El problema, en cuatro dimensiones.

Bloque 1
▎ Tecnológico

Red sin segmentar

Voz y datos compiten en el mismo dominio de broadcast. Latencia, congestión y vulnerabilidades laterales.

▎ Económico

Telefonía tradicional

Costos operativos altos. Una red convergente reduce gasto en líneas y centralizada el aprovisionamiento.

▎ Social

Comunicación interna

Coordinación deficiente entre áreas (TI, Finanzas, Ventas) impacta directamente la calidad del servicio al cliente.

▎ Político / Ecológico

Transformación digital

El Perú impulsa modernización tecnológica. Digitalizar reduce hardware físico y consumo energético asociado.

— Análisis SEPTE

Meacom Data opera en servicios tecnológicos pero su propia red interna no refleja esa madurez. El diagnóstico SEPTE confirma que el problema cruza cuatro dimensiones a la vez.

— Hipótesis del proyecto

Una red convergente con VLANs, DHCP centralizado y telefonía IP integrada resuelve los cuatro frentes con una sola arquitectura.

— Capítulo 3 / Implementación

Router-on-a-Stick + DHCP centralizado.

Bloque 3

Una sola interfaz física Fa0/0 de R1 sostiene cinco sub-interfaces 802.1Q + una nativa. El mismo router corre 5 pools DHCP que entregan IP, gateway y DNS automáticamente.

! Sub-interfaz por VLAN — Inter-VLAN Routing interface FastEthernet0/0.10 encapsulation dot1Q 10 ip address 192.168.10.1 255.255.255.0 ! Pool DHCP de la VLAN VOIP — note la option 150 ip dhcp pool VOIP network 192.168.50.0 255.255.255.0 default-router 192.168.50.1 option 150 ip 192.168.50.1
▎ ¿Qué es option 150?

Es la opción DHCP que indica al teléfono IP dónde está el servidor TFTP que le entregará su firmware y configuración. Sin esta opción, los IP Phones se quedan boot-loop sin registrarse. En Meacom Data el TFTP es el mismo R1 (CME corre embebido).

▎ DNS centralizado

Todos los pools (excepto VOIP) apuntan al servidor 192.168.99.20 en la VLAN de administración. Resolución única para el dominio meacomdata.local.

RoaS DHCP × 5 pools DNS centralizado OSPF area 0

— Hardening de red · enfoque de carrera

Siete capas de defensa, no una.

Bloque 4
— 01
SSH v2 forzado

transport input ssh en VTY. Telnet bloqueado, encriptación obligatoria.

— 02
Native VLAN ≠ 1

Trunks usan native vlan 999. Defensa contra VLAN hopping.

— 03
Puertos en parking

Toda interfaz no usada cae a VLAN 999 sin ruta. Cualquier intruso queda aislado.

— 04
VLAN 1 apagada

interface Vlan1 → shutdown. La VLAN por defecto no enruta nada.

— 05
Passwords cifrados

service password-encryption + enable secret 5 con MD5.

— 06
Login local

Usuario admin con secret cifrado. Cuentas individuales, no compartidas.

— 07 · BONUS
Trunks restringidos · switchport trunk allowed vlan 10,20,30,50,99,999

Solo las VLANs autorizadas viajan por el trunk. Bloqueo explícito de cualquier otra. Una capa más contra ataques de inserción de VLAN.

— Cierre

Lo que aprendimos y lo que sigue.

Bloque 4
01
Convergencia validada

VLANs + DHCP + Inter-VLAN routing + VoIP funcionan como un único sistema. Voz y datos coexisten sin pisarse.

02
Seguridad por diseño

Hardening desde el primer comando. SSH, parking VLAN, native VLAN custom y trunks restringidos no son extras — son parte de la base.

03
Listo para escalar

OSPF área 0 ya levantado, dominio meacomdata.local definido, esquema /24 uniforme. Agregar una sede más es replicar, no rediseñar.

— Recomendaciones
Migrar a GNS3 + VMware

Para integrar un servidor Linux real con BIND9 (DNS) y Apache (intranet) — y poder probar VPN IPsec Site-to-Site sobre routers con cripto real.

Servidor VoIP dedicado

Mover el call manager a un Asterisk o CUCM en VM independiente — escala a cientos de extensiones y libera al router del trabajo de telefonía.

Demo en vivo

Video de 3–5 min mostrando: ping inter-VLAN, IP recibida por DHCP, llamada VoIP entre sedes y registro de extensiones en CME.
